# Pack Pulse Next.js – corriger un problème du site en ligne

- **Constater** : la sonde vise `<adresse>/api/sante`, qui répond 200 quand la base répond et 503 sinon ; la page d'accueil, statique, peut rester affichée pendant une panne de la base. Un 503 sur `/api/sante` oriente vers Neon (base en veille, limite de l'offre gratuite atteinte, adresse `DATABASE_URL` changée), pas vers le code.
- **Journaux** : Vercel → le projet → **Logs** → filtre **Level** → **Error**. La référence montrée à l'écran par la page d'erreur (`digest`) se cherche dans la barre de recherche des journaux. Conservation : 1 heure sur l'offre Hobby, 1 jour sur Pro : ouvrir les journaux tout de suite. Le message d'une erreur de la base peut citer une valeur saisie par un visiteur : ne recopier que le type d'erreur.
- **Depuis la dernière mise en ligne** : Vercel → **Deployments** donne l'heure de chaque mise en ligne ; une construction en échec laisse la version d'avant en ligne (le problème vient alors d'ailleurs).
- **Contenir** : le retour arrière du site suit « Retour arrière » de `docs/technical.md` (Instant Rollback) ; il ne touche pas la base. Une migration appliquée reste appliquée : l'ancienne version doit pouvoir lire la base telle qu'elle est (`references/contexte/deploy.md`, migrations en deux mises en ligne).
- **Causes fréquentes propres à la production** : variable absente ou réservée à Preview (Settings → Environment Variables), `BETTER_AUTH_URL` ou `SITE_URL` différente de l'adresse réelle (connexion qui échoue), limite d'un service gratuit atteinte (Neon, Resend), clé d'un service tiers renouvelée d'un côté seulement.
- **Après la correction** : après un retour arrière, le correctif envoyé se construit sans passer en ligne. Une fois sa construction finie (**Deployments**), **Undo Rollback** (même tuile que le retour arrière) → choisir la version corrigée : elle passe en ligne et la mise en ligne automatique reprend (https://vercel.com/docs/instant-rollback) ; vérifier `/api/sante` de nouveau.
