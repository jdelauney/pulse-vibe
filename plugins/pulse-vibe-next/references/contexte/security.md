# Pack Pulse Next.js – pour la sécurité

## En-têtes de sécurité (`/pulse:security entetes`, point S12)

- **Où** : `next.config.ts`, fonction `headers()`, appliquée à toutes les adresses (`/:path*`). Le squelette envoie déjà sept en-têtes : `Content-Security-Policy`, `Strict-Transport-Security`, `Cross-Origin-Opener-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`. Projet créé avant pulse-vibe-next 0.9.0 (pas d'objet `sources`) : reprendre `next.config.ts` du squelette (constantes `sources`, `csp`, `entetesDeSecurite` et fonction `headers()`), en gardant les autres réglages du projet.
- **Ajouter un service à la CSP** : compléter l'objet `sources` de `next.config.ts`, dans la directive concernée (`connect-src` pour un appel depuis le navigateur, `img-src` pour une image, `script-src` pour un script, `frame-src` pour un contenu intégré : ajouter la clé `frame-src` si elle manque). Écrire l'adresse exacte donnée par la documentation du service. Garder un seul `headers()` : si deux règles posent le même en-tête sur la même adresse, la dernière remplace la première.
- **Pourquoi `'unsafe-inline'` dans `script-src`** : Next.js insère des scripts dans chaque page (les données de la page pour React). La documentation de Next.js propose deux méthodes : un nonce (une valeur différente à chaque visite) ou `'unsafe-inline'`. Un nonce oblige à recalculer chaque page à chaque visite : le prérendu (`cacheComponents`) et le cache disparaissent, le site devient plus lent et plus coûteux. Les empreintes (`experimental.sri`) couvrent seulement les fichiers de scripts : essayées avec Next.js 16.4.0, elles laissent bloqués les scripts insérés dans la page, et le site ne démarre plus. Le pack garde donc `'unsafe-inline'`. La CSP protège quand même : scripts limités au site et aux sources listées, aucun plugin, aucun envoi de formulaire ailleurs, aucun affichage dans un cadre. L'affichage sans injection repose sur React et sur `<JsonLd>` (S6).
- **HSTS** : `max-age=63072000; includeSubDomains`. Vercel envoie aussi cet en-tête ; la valeur du projet vaut chez tout hébergeur. L'option `preload` inscrit le domaine dans les navigateurs, pour tous ses sous-domaines, et se retire difficilement : l'ajouter seulement si la personne le décide, après lui avoir expliqué cette conséquence.
- **`proxy.ts`** (ajouté par la recette `connexion`) fait seulement un renvoi rapide vers la connexion. L'autorisation se décide côté serveur : `actionConnectee` pour les actions, `utilisateurConnecte()` pour les pages.
- **Sources ajoutées par les recettes** : `fichiers` ajoute l'hôte R2 du bucket à `connect-src` ; `mesure-reelle` (option A) ajoute `https://va.vercel-scripts.com` à `script-src`, en développement seulement ; `formulaire-public` (option Turnstile) ajoute `https://challenges.cloudflare.com` à `script-src` et à `frame-src`. Les autres recettes passent par le serveur et gardent la CSP telle quelle.
- **Prévisualisations Vercel** : Vercel y ajoute sa barre d'outils, chargée depuis `https://vercel.live`. La CSP la bloque, et la console affiche ces violations. Les accepter sur une prévisualisation, ou couper la barre dans les réglages du projet Vercel ; la CSP reste telle quelle.

## Vérifier

1. `npm run build`, puis `npm run start`.
2. `curl -sI http://localhost:3000` : les sept en-têtes apparaissent.
3. `npm run test:e2e` : `e2e/securite.spec.ts` vérifie les en-têtes servis et l'absence de violation de la CSP.
4. Après la mise en ligne : `curl -sI <adresse du site>` montre une seule ligne `strict-transport-security`, puis https://securityheaders.com.
