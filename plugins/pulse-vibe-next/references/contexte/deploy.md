# Pack Pulse Next.js – pour mettre en ligne

**Vercel** (hébergeur), **GitHub** (dépôt) et **Neon** (base) :

- Première mise en ligne : sur vercel.com, « Add New… → Project », importer le dépôt GitHub ; Vercel reconnaît Next.js. `vercel.json` fixe la région des fonctions (`fra1`, proche de Neon) et la commande de construction : `node scripts/migrer.mjs --vercel && npm run build` (migrations, puis construction).
- **Relier Neon à Vercel**, une fois, avant la première version qui lit la base en ligne (https://neon.com/docs/guides/neon-managed-vercel-integration) :
  1. Vercel → le projet → **Settings** → **Environment Variables** : si l'intégration affiche « Failed to set environment variables », supprimer ou renommer les variables déjà présentes `DATABASE_URL`, `PGHOST`, `PGUSER`, `PGDATABASE` et `PGPASSWORD` (l'intégration les écrit elle-même), puis recommencer. Cette suppression passe par la personne.
  2. Console Neon → **Integrations** → Vercel → **Add** → **Install from Vercel Marketplace** → **Install** → **Link Existing Neon Account** → **Continue** ; choisir le projet Vercel, puis le projet Neon, sa base et son rôle.
  3. Laisser décochée « Create a branch for your development environment » (le poste a déjà sa branche `dev`) ; cocher « Automatically delete obsolete Neon branches ».
  4. **Connect**, puis **Done**.
  Résultat : Production lit la branche principale (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`) ; chaque prévisualisation reçoit sa propre branche `preview/<branche Git>`, copie de la production, supprimée avec la branche Git. Un mot de passe renouvelé dans Neon est recopié dans Vercel par l'intégration.
- **Sauvegarde avant migration**, en Production : console Neon → **Settings** (de l'organisation) → **API keys** → **Create new** → **Project-scoped** → le projet du site (sans ce choix, une clé personnelle : **Account settings** → **API keys**). La clé s'affiche une seule fois : `pulse-aidd secrets preparer NEON_API_KEY --fichier .env.envoi`, la personne y colle la clé. L'identifiant du projet (console Neon → le projet → **Settings** → **General** → **Project ID**, pas un secret) : la personne ajoute la ligne `NEON_PROJECT_ID=<identifiant>` dans `.env.envoi`, et le saisit aussi dans Vercel comme `NEON_PROJECT_ID`, pour Production, en type Config. Puis `pulse-aidd secrets verifier NEON_API_KEY --fichier .env.envoi` (la clé lit le projet), et `pulse-aidd secrets envoyer NEON_API_KEY --env production --depuis .env.envoi --vider`.
- **Migrations** : automatiques, avant chaque construction (`scripts/migrer.mjs`). Prévisualisation : appliquées à sa branche. Production : quand une migration reste à appliquer, branche Neon `sauvegarde-AAAAMMJJ-HHMM` (gardée 7 jours ; sans date si Neon refuse l'expiration : le nettoyage la retire alors), puis migration. Un échec arrête la construction : la version en ligne reste celle d'avant. Sur Vercel, seule `DATABASE_URL_UNPOOLED` (posée par l'intégration) désigne la base : sans elle, la construction s'arrête avec la consigne de relier Neon. Le code de la version précédente sert encore pendant la construction : retirer ou renommer une colonne ou une table, ou changer son type, se fait en deux mises en ligne (d'abord le code qui ne l'emploie plus ou accepte les deux formes, puis la migration). Première mise en ligne : si `drizzle/` contient déjà des migrations, la première construction s'arrête tant que Neon n'est pas relié ; c'est normal : relier Neon (ci-dessus), puis **Redeploy**. Neon limite le nombre de branches (10 sur les offres Free et Launch) : avant chaque sauvegarde, le script supprime les branches `sauvegarde-…` au-delà des 2 plus récentes ; si la limite est quand même atteinte, la construction s'arrête avec la consigne de supprimer d'anciennes branches dans la console Neon. Il lui faut l'accès aux variables système de Vercel (Settings → Environment Variables → case « Enable access to System Environment Variables » : vérifier qu'elle est cochée).
- **Variables d'environnement**, pour Production et Preview : celles de `.env.example`, sauf `DATABASE_URL` et `DATABASE_URL_DIRECT` (l'intégration fournit les adresses de chaque environnement). Avec le Vercel CLI relié (`vercel login`, puis `vercel link`) : `pulse-aidd secrets envoyer <NOM> --env production,preview` (valeur par l'entrée standard, type Secret) ; une variable propre à chaque environnement (adresse du site, clés Stripe) part en production depuis `.env.envoi` ; une valeur par environnement pour les secrets générés (`pulse-aidd secrets generer <NOM> --envoyer production,preview`) ; puis `pulse-aidd secrets redeployer`. Sans CLI : la personne les saisit dans Project → Settings → Environment Variables, en type Secret, puis Deployments → … → Redeploy.
- **better-auth** (recette connexion) : `BETTER_AUTH_URL` = l'adresse du site en production ; ajouter l'adresse de prévisualisation aux origines de confiance si besoin.
- **Adresse du site** : quand le domaine est définitif, la personne saisit `SITE_URL` (ex. `https://www.mon-site.fr`) dans les variables de Production, puis redéploie ; sans elle, le site déclare le domaine de production fourni par Vercel.
- **Retour arrière** : « Retour arrière » des valeurs de `docs/technical.md` du pack (`pulse-aidd pile reference technical.md`), recopié dans `docs/technical.md` du projet.
- Preuve : `pulse-aidd sonder <adresse> --texte "<nom du projet>"`, puis `pulse-aidd seo <adresse> --essentiel`.
- IndexNow (facultatif, si `public/<clé>.txt` existe) : envoi après les preuves, d'après « IndexNow » des consignes Search Console du pack (`pulse-aidd pile reference contexte/search-console.md`).

**CI (GitHub Actions)**, pour `/pulse:cicd` : Node.js LTS récent, `npm ci`, `node scripts/verifier.js`, `npm run check`, `npm run typecheck`, `npm test`, `npm run build` avec `SKIP_ENV_VALIDATION=1` (la CI n'a pas les secrets ; t3 env saute alors la validation). Bout en bout en CI : `npx playwright install --with-deps chromium`, puis `npm run test:e2e` (avec `CI=true` et `SKIP_ENV_VALIDATION=1`).
- Commande de construction avec les contrôles (`/pulse:deploy` § 5.1, quand la CI ou le mode production sont ajoutés) : dans `vercel.json`, `buildCommand` devient `node scripts/verifier.js && npm run check && npm run typecheck && npm test && node scripts/migrer.mjs --vercel && npm run build` (les migrations restent juste avant la construction).
- Surveillance (`/pulse:deploy` § 5) : sonde de disponibilité sur l'adresse de production. Les erreurs techniques se lisent dans les journaux de l'hébergeur (Vercel → Logs) : le `logger` du squelette (pino) y écrit côté serveur.
