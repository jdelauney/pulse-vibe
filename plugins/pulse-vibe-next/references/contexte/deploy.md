# Pack Pulse Next.js – pour mettre en ligne

**Vercel** (hébergeur), **GitHub** (dépôt) et **Neon** (base) :

- Première mise en ligne : sur vercel.com, « Add New… → Project », importer le dépôt GitHub ; Vercel reconnaît Next.js. `vercel.json` fixe la région des fonctions (`fra1`, proche de Neon) et la commande de construction : `npm test && node scripts/migrer.mjs --vercel && npm run build` (tests unitaires et d'intégration, migrations, puis construction). Les tests allongent chaque construction, prévisualisations comprises. Un test qui échoue arrête la construction avant toute migration, en Production comme en prévisualisation : la version en ligne reste celle d'avant, même pour un envoi sur `main` fait hors de `/pulse:deploy`, et la prévisualisation n'est pas créée tant que le test échoue. Biome et les tests de bout en bout tournent dans la CI (`/pulse:cicd`).
- **Relier Neon à Vercel**, une fois, avant la première version qui lit la base en ligne (https://neon.com/docs/guides/neon-managed-vercel-integration) :
  1. Vercel → le projet → **Settings** → **Environment Variables** : si l'intégration affiche « Failed to set environment variables », supprimer ou renommer les variables déjà présentes `DATABASE_URL`, `PGHOST`, `PGUSER`, `PGDATABASE` et `PGPASSWORD` (l'intégration les écrit elle-même), puis recommencer. Cette suppression passe par la personne.
  2. Console Neon → **Integrations** → Vercel → **Add** → **Install from Vercel Marketplace** → **Install** → **Link Existing Neon Account** → **Continue** ; choisir le projet Vercel, puis le projet Neon, sa base et son rôle.
  3. Laisser décochée « Create a branch for your development environment » (le poste a déjà sa branche `dev`) ; cocher « Automatically delete obsolete Neon branches ».
  4. **Connect**, puis **Done**.
  Résultat : Production lit la branche principale (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`) ; chaque prévisualisation reçoit sa propre branche `preview/<branche Git>`, copie de la production, supprimée avec la branche Git. Un mot de passe renouvelé dans Neon est recopié dans Vercel par l'intégration.
- **Sauvegarde avant migration**, en Production : console Neon → **Settings** (de l'organisation) → **API keys** → **Create new** → **Project-scoped** → le projet du site (sans ce choix, une clé personnelle : **Account settings** → **API keys**). La clé s'affiche une seule fois : `pulse-aidd secrets preparer NEON_API_KEY --fichier .env.envoi`, la personne y colle la clé. L'identifiant du projet (console Neon → le projet → **Settings** → **General** → **Project ID**, pas un secret) : la personne ajoute la ligne `NEON_PROJECT_ID=<identifiant>` dans `.env.envoi`, et le saisit aussi dans Vercel comme `NEON_PROJECT_ID`, pour Production, en type Config. Avant l'envoi, `vercel login` puis `vercel link` (le CLI Vercel doit être connecté et lié au projet). Puis `pulse-aidd secrets verifier NEON_API_KEY --fichier .env.envoi` (la clé lit le projet), et `pulse-aidd secrets envoyer NEON_API_KEY --env production --depuis .env.envoi --vider`. Le même envoi enregistre tout seul `NEON_ENDPOINT_PRODUCTION` dans Vercel, pour Preview, en type Config : l'outil lit chez Neon le point d'accès de la branche principale (rien à saisir ; il sert à la garde des prévisualisations de `scripts/migrer.mjs`). Sans le CLI Vercel : console Neon → branche principale → Computes → identifiant `ep-…` → Vercel, Preview, type Config, `NEON_ENDPOINT_PRODUCTION`. S'il n'a pas pu partir (Neon injoignable, `NEON_PROJECT_ID` absent de `.env.envoi`), la clé reste dans `.env.envoi` et le message dit quoi régler avant de relancer la même commande. Vercel ne permet pas de réserver une variable à la construction : `NEON_API_KEY` est aussi lisible par le code du site en Production. Le squelette ne la lit qu'à la construction (`scripts/migrer.mjs`) ; une clé limitée au projet, créée pour ce seul usage et renouvelée chaque année (tout de suite après un doute), limite ce qu'une fuite permettrait.
- **Migrations** : automatiques, avant chaque construction (`scripts/migrer.mjs`). Prévisualisation : appliquées à sa branche, après vérification qu'elle n'est pas la production (`NEON_ENDPOINT_PRODUCTION`, enregistré par l'envoi de la clé Neon) ; si elle utilise la production, ou si le repère manque, les migrations sont sautées avec un message dans le journal de construction et la construction continue (la prévisualisation peut alors afficher des erreurs ; le message dit comment y remédier). Production : quand une migration reste à appliquer, branche Neon `sauvegarde-AAAAMMJJ-HHMM` (gardée 7 jours ; sans date si Neon refuse l'expiration : le nettoyage la retire alors), puis migration. Un échec arrête la construction : la version en ligne reste celle d'avant. Sur Vercel, seule `DATABASE_URL_UNPOOLED` (posée par l'intégration) désigne la base : sans elle, la construction s'arrête avec la consigne de relier Neon. Le code de la version précédente sert encore pendant la construction : retirer ou renommer une colonne ou une table, ou changer son type, se fait en deux mises en ligne (d'abord le code qui ne l'emploie plus ou accepte les deux formes, puis la migration). Première mise en ligne : si `drizzle/` contient déjà des migrations, la première construction s'arrête tant que Neon n'est pas relié ; c'est normal : relier Neon (ci-dessus), puis **Redeploy**. Neon limite le nombre de branches (10 sur les offres Free et Launch) : avant chaque sauvegarde, le script supprime les branches `sauvegarde-…` au-delà des 2 plus récentes ; si la limite est quand même atteinte, la construction s'arrête avec la consigne de supprimer d'anciennes branches dans la console Neon. Il lui faut l'accès aux variables système de Vercel (Settings → Environment Variables → case « Enable access to System Environment Variables » : vérifier qu'elle est cochée).
- **Variables d'environnement**, pour Production et Preview : celles de `.env.example`, sauf `DATABASE_URL` et `DATABASE_URL_DIRECT` (l'intégration fournit les adresses de chaque environnement). Chaque variable obligatoire de `src/config/env.ts` est saisie dans les deux environnements : la validation t3 env arrête une construction où l'une manque. Avec le Vercel CLI relié (`vercel login`, puis `vercel link`) : `pulse-aidd secrets envoyer <NOM> --env production,preview` (valeur par l'entrée standard, type Secret) pour une variable qui a la même valeur partout ; une variable propre à chaque environnement (adresse du site) part en production depuis `.env.envoi` ; une valeur par environnement pour les secrets générés (`pulse-aidd secrets generer <NOM> --envoyer production,preview`) ; puis `pulse-aidd secrets redeployer`. Sans CLI : la personne les saisit dans Project → Settings → Environment Variables, en type Secret, puis Deployments → … → Redeploy. **Deux envois pour ce qui agit sur le monde réel** (SMTP, clés Stripe) : une fois en Production avec la valeur réelle, depuis `.env.envoi` (`pulse-aidd secrets envoyer <NOM> --env production --depuis .env.envoi --vider`), et une fois en Preview avec une valeur de test (`--env preview` ; valeur lue dans `.env` ; `--depuis <fichier>` pour une autre). En Preview : un SMTP de test (le bac à sable du fournisseur d'e-mail, ou un service qui capture les messages : un faux serveur d'envoi, qui ne livre rien) et des clés de test (Stripe `sk_test_…`). Chaque prévisualisation travaille sur une copie des données réelles (comptes, adresses e-mail) : avec le SMTP réel, elle pourrait écrire à de vrais clients. Vérifier que la protection des prévisualisations est active (Vercel → Settings → **Deployment Protection** → **Vercel Authentication**) : seules les personnes de l'équipe Vercel les ouvrent.
- **better-auth** (recette connexion) : `BETTER_AUTH_URL` = l'adresse du site en production ; ajouter l'adresse de prévisualisation aux origines de confiance si besoin.
- **Adresse du site** : quand le domaine est définitif, la personne saisit `SITE_URL` (ex. `https://www.mon-site.fr`) dans les variables de Production, puis redéploie ; sans elle, le site déclare le domaine de production fourni par Vercel.
- **Retour arrière** : « Retour arrière » des valeurs de `docs/technical.md` du pack (`pulse-aidd pile reference technical.md`), recopié dans `docs/technical.md` du projet.
- Preuve : `pulse-aidd sonder <adresse> --texte "<nom du projet>"`, puis `pulse-aidd seo <adresse> --essentiel`.
- IndexNow (facultatif, si `public/<clé>.txt` existe) : envoi après les preuves, d'après « IndexNow » des consignes Search Console du pack (`pulse-aidd pile reference contexte/search-console.md`).

**CI (GitHub Actions)**, pour `/pulse:cicd` : Node.js LTS récent, `npm ci`, `node scripts/verifier.js`, `npm run check`, `npm run typecheck`, `npm test`, `npm run build` avec `SKIP_ENV_VALIDATION=1` (la CI n'a pas les secrets ; t3 env saute alors la validation). Bout en bout en CI : `npx playwright install --with-deps chromium`, puis `npm run test:e2e` (avec `CI=true` et `SKIP_ENV_VALIDATION=1`).
- Commande de construction avec les contrôles (`/pulse:deploy` § 5.1, quand la CI ou le mode production sont ajoutés) : dans `vercel.json`, `buildCommand` devient `node scripts/verifier.js && npm run check && npm run typecheck && npm test && node scripts/migrer.mjs --vercel && npm run build` (les migrations restent juste avant la construction).
- Surveillance (`/pulse:deploy` § 5) :
  - **Sonde de disponibilité** : tant que le site ne lit pas la base, sur l'adresse de production ; ensuite sur `<adresse>/api/sante`, qui répond 503 quand la base ne répond plus (la page d'accueil, statique, resterait affichée). La sonde vise l'adresse exacte `/api/sante`, sans paramètre ; son option anti-cache, si elle en propose une, reste désactivée : une chaîne de requête ajoutée à l'adresse contourne le cache de Vercel, et la base serait alors interrogée à chaque appel. Fréquence : toutes les 15 à 30 minutes, pas plus souvent. La réponse « ok » est gardée 15 minutes par Vercel, donc la base est interrogée au plus une fois par quart d'heure : Neon peut se mettre en veille entre deux appels. Une base sondée toutes les quelques minutes ne se met jamais en veille et dépasse les 100 CU-h par mois de l'offre gratuite (la base est alors suspendue jusqu'à la fin du mois). Une panne est donc vue avec jusqu'à 15 minutes de retard. La sonde prévient la personne par e-mail.
  - **Journaux** : Vercel → le projet → **Logs** → filtre **Level** → **Error**. On y trouve les erreurs du serveur (le `logger` du squelette les écrit sur la sortie d'erreur) et celles du navigateur (message « Erreur dans le navigateur », envoyées par `app/error.tsx` et `app/global-error.tsx`). Dans ces dernières, les adresses e-mail sont masquées et les adresses web perdent leur chaîne de requête ; les segments du chemin (`/compte/42`) et les numéros de téléphone restent visibles. La référence affichée à la personne (`digest`) se cherche dans la barre de recherche. Limites connues : un message de Postgres peut citer la valeur saisie ; Next écrit les erreurs de rendu hors du `logger` ; les journaux de requêtes de Vercel montrent l'adresse complète. Durée de conservation : **1 heure** sur l'offre Hobby, 1 jour sur Pro (https://vercel.com/docs/logs/runtime) : après une alerte, ouvrir les journaux tout de suite.
  - **Essai après la mise en ligne** : ouvrir `<adresse>/essai-surveillance`, cliquer sur « Déclencher une erreur d'essai », puis retrouver la ligne « Erreur dans le navigateur » dans les journaux.
  - Limites : aucune alerte sur le nombre d'erreurs (il faudrait un drain de journaux, payant, ou un service tiers, écarté pour rester simple) ; les envois du navigateur sont limités à 10 par minute et par adresse IP, pour chaque instance du site.
