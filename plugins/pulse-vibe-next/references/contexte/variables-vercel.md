# Pack Pulse Next.js – variables d'environnement chez Vercel

Affiché pour `/pulse:secrets` et pour la mise en ligne (`pulse-aidd pile contexte deploy-variables`).

- **Envoi automatique** : `pulse-aidd secrets envoyer` passe la valeur à `vercel env update` (variable existante) ou `vercel env add … --type secret` (nouvelle), **par l'entrée standard**. Prérequis sur le poste : le Vercel CLI (`npm install -g vercel`), `vercel login`, puis `vercel link` dans le dossier du projet (crée `.vercel/`, déjà ignoré par Git). Sans CLI : la personne saisit la valeur dans Project → Settings → Environment Variables, en type Secret, puis Deployments → … → Redeploy.
- **Type Secret** pour tout secret : sa valeur ne se relit plus, ni par l'équipe ni par le CLI. Une variable déjà enregistrée en type Config se supprime dans les réglages (par la personne), puis se renvoie : elle revient en Secret. Production et Preview sont en Secret par défaut ; Development accepte aussi les Secrets.
- **Quelles variables** : pour Production et Preview, celles de `.env.example`, sauf `DATABASE_URL` et `DATABASE_URL_DIRECT` (l'intégration Vercel–Neon fournit les adresses de chaque environnement). Chaque variable obligatoire de `src/config/env.ts` est saisie dans les deux environnements : la validation t3 env arrête une construction où l'une manque.
- **Valeurs distinctes** : Production et Preview reçoivent chacune leur valeur pour les secrets générés (`pulse-aidd secrets generer <NOM> --envoyer production,preview`). Les adresses de la base viennent de l'intégration Vercel–Neon (une branche par prévisualisation) ; des clés de test (Stripe, R2) en Preview évitent de toucher aux données réelles. Les variables propres à chaque environnement (`DATABASE_URL`, `DATABASE_URL_DIRECT`, `BETTER_AUTH_URL`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`) reçoivent en production leur propre valeur (l'intégration Vercel–Neon pour la base, `.env.envoi` pour les autres) : `pulse-aidd secrets envoyer` depuis `.env` vers la production s'arrête pour elles.
- **Deux envois pour ce qui agit sur le monde réel** (SMTP, clés Stripe) : une fois en Production avec la valeur réelle, depuis `.env.envoi` (`pulse-aidd secrets envoyer <NOM> --env production --depuis .env.envoi --vider`), et une fois en Preview avec une valeur de test (`--env preview` ; valeur lue dans `.env` ; `--depuis <fichier>` pour une autre). En Preview : un SMTP de test (le bac à sable du fournisseur d'e-mail, ou un service qui capture les messages : un faux serveur d'envoi, qui ne livre rien) et des clés de test (Stripe `sk_test_…`). Chaque prévisualisation travaille sur une copie des données réelles (comptes, adresses e-mail) : avec le SMTP réel, elle pourrait écrire à de vrais clients. Vérifier que la protection des prévisualisations est active (Vercel → Settings → **Deployment Protection** → **Vercel Authentication**) : seules les personnes de l'équipe Vercel les ouvrent.
- **Une variable modifiée sert au déploiement suivant** : les déploiements existants gardent l'ancienne valeur. `pulse-aidd secrets redeployer --env production` relance le dernier déploiement prêt (`vercel redeploy`). Les adresses de prévisualisation se reconstruisent au prochain envoi de la branche ; une ancienne adresse de prévisualisation cesse de marcher quand l'ancienne valeur est révoquée : c'est attendu.
- **Variables propres à une branche Git** : l'adaptateur les laisse de côté ; elles se gèrent dans les réglages Vercel.

Sources : https://vercel.com/docs/cli/env (màj 2026-08-20), https://vercel.com/docs/environment-variables/rotating-secrets (màj 2026-07-15), https://vercel.com/docs/environment-variables/sensitive-environment-variables (màj 2026-08-28), https://vercel.com/docs/cli/redeploy (màj 2026-03-17).
