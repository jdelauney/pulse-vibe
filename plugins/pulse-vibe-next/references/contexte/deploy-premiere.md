# Pack Pulse Next.js – première mise en ligne

- Première mise en ligne : sur vercel.com, « Add New… → Project », importer le dépôt GitHub ; Vercel reconnaît Next.js. `vercel.json` fixe la région des fonctions (`fra1`, proche de Neon) et la commande de construction : `npm test && node scripts/migrer.mjs --vercel && npm run build` (tests unitaires et d'intégration, migrations, puis construction). Les tests allongent chaque construction, prévisualisations comprises. Biome et les tests de bout en bout tournent dans la CI (`/pulse:cicd`).
- **Relier Neon à Vercel**, une fois, avant la première version qui lit la base en ligne (https://neon.com/docs/guides/neon-managed-vercel-integration), puis préparer la sauvegarde avant migration. Une étape à la fois : la personne fait l'action, puis la vérification se fait avant l'étape suivante. Les boutons sont en anglais : donner le nom exact à cliquer, avec sa traduction entre parenthèses. Avant la première étape, `vercel login`, puis `vercel link` (le CLI Vercel connecté et lié au projet : il sert aux vérifications par `pulse-aidd secrets inventaire` et à l'envoi de l'étape 6).
  1. Vercel → le projet → **Settings** (réglages) → **Environment Variables** (variables d'environnement) : si les variables `DATABASE_URL`, `PGHOST`, `PGUSER`, `PGDATABASE` ou `PGPASSWORD` y figurent déjà, la personne les supprime (l'intégration les écrit elle-même ; sinon elle affiche « Failed to set environment variables »). Vérifier : `pulse-aidd secrets inventaire` ne montre plus ces noms en Production (sans Vercel CLI relié : la personne relit la liste à l'écran).
  2. Console Neon → **Integrations** (intégrations) → Vercel → **Add** → **Install from Vercel Marketplace** → **Install** → **Link Existing Neon Account** (relier le compte Neon existant) → **Continue** ; choisir le projet Vercel, puis le projet Neon, sa base et son rôle ; laisser décochée « Create a branch for your development environment » (le poste a déjà sa branche `dev`), cocher « Automatically delete obsolete Neon branches », puis **Connect** et **Done**. Vérifier : `pulse-aidd secrets inventaire` montre `DATABASE_URL_UNPOOLED` en Production (les variables des prévisualisations, propres à chaque branche Git, n'y figurent pas : c'est normal).
  3. Résultat, à dire en une phrase : Production lit la branche principale de Neon (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`) ; chaque prévisualisation reçoit sa propre branche `preview/<branche Git>`, copie de la production, supprimée avec la branche Git ; un mot de passe renouvelé dans Neon est recopié dans Vercel par l'intégration. Vérifier : après le prochain envoi d'une branche de travail, le journal de construction de sa prévisualisation (Vercel → **Deployments**) affiche les migrations appliquées, sans le message « reliez Neon à Vercel » (la personne lit le journal ; sinon, passer à l'étape suivante).
  4. **Clé pour la sauvegarde** : console Neon → **Settings** (de l'organisation) → **API keys** → **Create new** → **Project-scoped** (limitée à un projet) → le projet du site (sans ce choix, une clé personnelle : **Account settings** → **API keys**). La clé s'affiche une seule fois : `pulse-aidd secrets preparer NEON_API_KEY --fichier .env.envoi`, puis la personne y colle la clé dans son éditeur. Vérifier : `pulse-aidd secrets verifier NEON_API_KEY --fichier .env.envoi --sans-test` (présente, sans espace ni guillemet en trop).
  5. **Identifiant du projet** (pas un secret) : console Neon → le projet → **Settings** → **General** → **Project ID** ; la personne ajoute la ligne `NEON_PROJECT_ID=<identifiant>` dans `.env.envoi`. Vérifier : `pulse-aidd secrets verifier NEON_API_KEY --fichier .env.envoi` (la clé lit bien ce projet chez Neon).
  6. **Envoi chez Vercel**, en Production seulement : `pulse-aidd secrets envoyer NEON_PROJECT_ID --env production --depuis .env.envoi` (l'outil choisit le type Config ; la ligne reste dans le fichier pour l'envoi suivant), puis `pulse-aidd secrets envoyer NEON_API_KEY --env production --depuis .env.envoi --vider` (type Secret ; la clé quitte le fichier). Le même envoi enregistre `NEON_ENDPOINT_PRODUCTION` tout seul, pour Preview : l'outil lit chez Neon le point d'accès de la branche principale (rien à saisir) ; il sert à la garde des prévisualisations de `scripts/migrer.mjs`. S'il n'a pas pu partir (Neon injoignable, `NEON_PROJECT_ID` absent de `.env.envoi`), la clé reste dans `.env.envoi` et le message dit quoi régler avant de relancer la même commande. Sans le CLI Vercel : la personne saisit dans Vercel → **Settings** → **Environment Variables** `NEON_PROJECT_ID` (Production, type Config), `NEON_API_KEY` (Production, type Secret) et `NEON_ENDPOINT_PRODUCTION` (Preview, type Config, identifiant `ep-…` : console Neon → branche principale → **Computes**). Vérifier : `pulse-aidd secrets inventaire` montre `NEON_PROJECT_ID` et `NEON_API_KEY` en Production, et `NEON_ENDPOINT_PRODUCTION` en Preview (sans Vercel CLI relié : la personne relit la liste à l'écran) ; après la prochaine mise en ligne, si une migration est à appliquer, le journal de construction affiche « Sauvegarde créée ».
  Vercel ne permet pas de réserver une variable à la construction : `NEON_API_KEY` est aussi lisible par le code du site en Production. Le squelette ne la lit qu'à la construction (`scripts/migrer.mjs`) ; une clé limitée au projet, créée pour ce seul usage et renouvelée chaque année (tout de suite après un doute), limite ce qu'une fuite permettrait.
- **Migrations** (en ligne) : Prévisualisation : appliquées à sa branche, après vérification qu'elle n'est pas la production (`NEON_ENDPOINT_PRODUCTION`, enregistré par l'envoi de la clé Neon) ; si elle utilise la production, ou si le repère manque, les migrations sont sautées avec un message dans le journal de construction et la construction continue (la prévisualisation peut alors afficher des erreurs ; le message dit comment y remédier). Production : quand une migration reste à appliquer, branche Neon `sauvegarde-AAAAMMJJ-HHMM` (gardée 7 jours ; sans date si Neon refuse l'expiration : le nettoyage la retire alors), puis migration. Sur Vercel, seule `DATABASE_URL_UNPOOLED` (posée par l'intégration) désigne la base : sans elle, la construction s'arrête avec la consigne de relier Neon. Première mise en ligne : si `drizzle/` contient déjà des migrations, la première construction s'arrête tant que Neon n'est pas relié ; c'est normal : relier Neon (ci-dessus), puis **Redeploy**. Neon limite le nombre de branches (10 sur les offres Free et Launch) : avant chaque sauvegarde, le script supprime les branches `sauvegarde-…` au-delà des 2 plus récentes ; si la limite est quand même atteinte, la construction s'arrête avec la consigne de supprimer d'anciennes branches dans la console Neon. Il lui faut l'accès aux variables système de Vercel (Settings → Environment Variables → case « Enable access to System Environment Variables » : vérifier qu'elle est cochée).
