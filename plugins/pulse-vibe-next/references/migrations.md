# Pack Pulse Next.js – mettre à niveau un projet plus ancien

Notes lues par `/pulse:init` (« Remettre les contrôles du projet à jour »). Chaque note commence par la version du pack qui a apporté le changement, puis le signe qui le révèle dans le projet : une note dont le signe est absent ne s'applique pas. Les notes s'appliquent de la plus ancienne à la plus récente, avec l'accord de la personne, puis `npm run check && npm run typecheck && npm test`.

- **Projet créé avant pulse-next 0.51.0** (`app/globals.css` commence par `@import "tailwindcss";`, sans `source(none)`) : écrire `@import "tailwindcss" source(none);` à la place, puis, après le dernier `@import`, `@source "../app";` et `@source "../src";`. Tailwind ne parcourt plus que ces deux dossiers ; dans le bac à sable de Claude Code, la construction s'arrêtait sur les fichiers à point qu'il rend illisibles.
- **Projet créé avant pulse-next 0.9.0** (`next.config.ts` sans objet `sources`) : reprendre `next.config.ts` du squelette (constantes `sources`, `csp`, `entetesDeSecurite` et fonction `headers()`), en gardant les autres réglages du projet.
- **Projet créé avant pulse-next 0.11.0** (`envServeur()`, `src/db/index.ts`) : `npm install @t3-oss/env-nextjs`, reprendre du squelette `src/config/env.ts`, `src/config/env-public.ts`, `src/config/env-commun.ts`, `src/db/db-client.ts`, `tests/helpers/env-de-test.ts` et le réglage `env` de `vitest.config.ts` ; reporter les variables du projet dans `server` d'`env.ts` (secrets) ou dans `client` + `experimental__runtimeEnv` d'`env-public.ts` (publiques, lues par `envPublic` dans les composants client), et les vérifications croisées dans `verificationsCroisees` d'`env.ts` ; supprimer `src/db/index.ts` ; remplacer `envServeur().X` par `env.X` et `@src/db` par `@src/db/db-client` ; dans les tests, `{ envServeur: () => ({…}) }` devient `{ env: {…} }`.
- **Projet créé avant pulse-next 0.17.0** (pas de `scripts/migrer.mjs`) : reprendre du squelette `scripts/migrer.mjs`, `tests/migrer.test.ts`, `vercel.json`, `drizzle.config.ts`, `instrumentation.ts`, `src/lib/errors/erreur-de-requete.ts` (et son test), `src/lib/logger.ts`, `app/error.tsx`, `app/global-error.tsx`, `e2e/accueil.spec.ts`, et le lien d'évitement de `app/layout.tsx` (balise `<a href="#contenu">` et `<div id="contenu">`) ; dans `src/lib/safe-action.ts`, reprendre `defineMetadataSchema`, `handleServerError` et le `.use()` du squelette en gardant `actionConnectee`, puis donner un nom à chaque action (`.metadata({ nom: "…" })` : `npm run typecheck` liste celles qui en manquent) ; `npm uninstall ws @types/ws`, `npm install -D @axe-core/playwright`, `shadcn` passé en `devDependencies`, `"engines": { "node": ">=22.19.0" }` dans `package.json` ; `.gitattributes` (`* text=auto eol=lf`) et `.npmrc` (`save-exact=true`) ; si `docs/design.md` ne prévoit pas de mode sombre : `npm uninstall next-themes` et, dans `src/components/ui/sonner.tsx`, `theme="light"` à la place de `useTheme()` ; si le mode sombre est prévu, `next-themes` et `useTheme()` restent (`references/theme.md`, « Mode sombre »). Puis séparer la base de développement de la production (« Mise en place » et « Pour mettre en ligne » du pack).
- **Projet créé avant pulse-next 0.22.0** (`src/lib/logger.ts` sans `serialiserErreur`) : reprendre du squelette `src/lib/logger.ts` et son test, `src/lib/errors/erreur-de-requete.ts`, `src/lib/errors/erreur-client.ts`, `src/lib/errors/signaler-erreur-client.ts`, `src/lib/sante.ts` (et leurs tests), `app/api/erreur-client/route.ts`, `app/api/sante/route.ts`, `app/error.tsx`, `app/global-error.tsx`, `scripts/migrer.mjs`, `tests/migrer.test.ts`, `vercel.json`, `playwright.config.ts` (le port est lu dans `PORT`), `e2e/accueil.spec.ts` (son test axe passe dans `accessibilite.spec.ts`), `e2e/aides/accessibilite.ts`, `e2e/accessibilite.spec.ts`, `e2e/erreur-client.spec.ts`, `src/components/ui/__tests__/cibles-tactiles.test.ts` ; dans `src/lib/safe-action.ts`, reprendre `requeteDu`, `handleServerError(erreur, { metadata, ctx })` et `next({ ctx: { requete } })` en gardant `actionConnectee` ; dans `src/components/ui/button.tsx` et `input.tsx`, reprendre les tailles (`h-11`) ; dans `app/globals.css`, `--muted-foreground` et `--chart-1` à `--chart-5` (`:root` et `.dark`) ; dans `src/config/env.ts`, reprendre `verificationsCroisees` et `createFinalSchema` du squelette (et son test `src/config/__tests__/env-verifications.test.ts`), puis transformer chaque `createFinalSchema` d'une recette (option Redis de `limite`, option Turnstile de `formulaire-public`) en `verificationsCroisees.push(…)`, comme dans la recette. Puis le repère de la production pour les prévisualisations : si `pulse-aidd secrets inventaire` ne montre pas `NEON_ENDPOINT_PRODUCTION` en Preview, et si `NEON_API_KEY` et `NEON_PROJECT_ID` sont encore remplis dans `.env.envoi`, `pulse-aidd secrets envoyer NEON_API_KEY --env production --depuis .env.envoi --vider` l'enregistre (une seule autorisation) ; sinon (la clé a quitté le fichier après son premier envoi, et Vercel ne la rend pas lisible), le renouvellement annuel de la clé l'enregistre (« Sauvegarde avant migration », « Pour mettre en ligne ») : le proposer maintenant, en une phrase. D'ici là, les prévisualisations sautent leurs migrations avec un message, sans arrêter la construction.
- **Projet créé ou mis à niveau avec pulse-next 0.22.0** (dossier `app/essai-surveillance/`, ou `app/[locale]/essai-surveillance/` avec la recette langues) : supprimer ce dossier s'il existe ; retirer aussi `"/essai-surveillance"` de `e2e/accessibilite.spec.ts` et, dans `e2e/erreur-client.spec.ts`, le test « une erreur dans la page est affichée puis signalée au serveur ». Les erreurs se suivent dans Vercel → Logs → filtre Level « Error ».
- **Projet créé avant pulse-next 0.30.1** (`package.json` avec `@axe-core/playwright` sans `"overrides"` pour `playwright-core`) : ajouter `"overrides": { "playwright-core": "$@playwright/test" }` dans `package.json`, puis `npm install`. Sans cet alignement, npm installe une autre version de `playwright-core` à côté de celle de `@playwright/test`, et `npm run typecheck` échoue dans `e2e/aides/accessibilite.ts`.
- **Projet créé avant pulse-next 0.47.0** (`biome.json` dont `files.includes` n'a pas `"!**/*.md"`) : ajouter `"!**/*.md"` à la fin de `files.includes` de `biome.json`. Biome met aussi en forme le Markdown : sans cette ligne, `npm run check` (et la vérification en ligne) refuse les documents de la méthode (`docs/`, `aidd_docs/`, `CLAUDE.md`) dès qu'un tableau n'est pas aligné.
- **Projet créé avant pulse-next 0.47.0** (polices par `next/font/google` dans `app/layout.tsx`) : pour servir les polices depuis le site, comme le squelette, lancer `pulse-aidd pile police "<famille du texte>"` (et `--role titres`, `--role code` pour les autres), retirer de `app/layout.tsx` l'import `next/font/google`, ses constantes et leurs `.variable` dans le `className` de `<html>`, puis ajouter `*.woff2 binary` à `.gitattributes`. Sans ce passage, le projet marche toujours : la construction télécharge les polices chez Google.
- **Projet créé avant pulse-next 0.48.0 avec la recette `connexion`** (`src/adapters/auth/auth.adapter.ts` sans `disabledPaths`) : le compte devient plus sûr. Reprendre de la recette `connexion` (étapes 3, 5, 6 et 8, et ses tests) les mots de passe compromis refusés (`src/core/compte/mot-de-passe-compromis.port.ts`, `src/adapters/hibp/hibp.adapter.ts`, `src/adapters/auth/mot-de-passe-compromis.ts`), les chemins fermés (`CHEMINS_FERMES`) et `tests/pages-connectees.test.ts` ; avec la recette `email`, reprendre aussi ses étapes 3 à 13 (lien de vérification valable 1 h, sans connexion automatique ; changement d'adresse et suppression du compte confirmés par e-mail) ; avec la recette `limite`, ses étapes 2, 6 et 7 (limites du changement et de la réinitialisation du mot de passe, refus journalisés). Le projet marche sans ce passage, avec les protections d'avant.
- **Projet créé avant pulse-next 0.53.0 avec la recette `email`** (`src/core/compte/email.port.ts`) : l'envoi des e-mails devient commun à toutes les fonctionnalités. Pour qu'une autre fonctionnalité envoie des e-mails, reprendre de la recette `envoi-email` ses étapes 2 à 4 et ses tests (`src/core/email/email.port.ts`, `src/adapters/email/nodemailer.adapter.ts`, `src/adapters/email/email.adapter.ts` qui remplace `NodemailerEmailAdapter`) ; les variables SMTP restent celles du projet. Puis remplacer `@src/core/compte/email.port` par `@src/core/email/email.port` dans les imports, passer `getEnvoyeurEmail()` à `creerAuth` dans `getAuth()` (étape 4 de la recette `email`), supprimer `src/core/compte/email.port.ts` ; les tests de la recette `envoi-email` remplacent l'ancien `src/adapters/email/__tests__/email.adapter.test.ts`. Le projet marche sans ce passage.
- **Projet créé avant pulse-next 0.54.0 avec la recette `fichiers`** (`src/adapters/storage/storage.adapter.ts` avec `StockageR2Adapter`, variables `R2_…`) : le projet marche sans changement, et son stockage reste le même. La recette vise désormais tout service compatible S3, et R2 en est un. Pour suivre la recette, avec l'accord de la personne : reprendre de la recette `fichiers` l'étape 6 (`StockageS3Adapter`), les lignes `S3_…` de l'étape 1 (`env.ts`, valeurs de test, `.env.example`), la CSP de l'étape 12 et le test de l'adapter ; puis renommer les variables, dans `.env` et chez l'hébergeur : `R2_ACCESS_KEY_ID` → `S3_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` → `S3_SECRET_ACCESS_KEY`, `R2_BUCKET` → `S3_BUCKET` (mêmes valeurs) ; `R2_ACCOUNT_ID` disparaît, remplacée par `S3_ENDPOINT=https://<R2_ACCOUNT_ID>.eu.r2.cloudflarestorage.com` (sans `.eu` si le bucket a été créé sans juridiction) et `S3_REGION=auto` ; `S3_FORCE_PATH_STYLE` reste à `false`. Redéployer ensuite : la CSP se fixe à la construction.
