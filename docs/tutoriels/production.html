Tutoriel 2 · Plusieurs séances

Mode complet : prêt pour de vrais clients

Le salon a vu son prototype et veut aller plus loin. Cette fois, on construit la vraie appli : une fonction à la fois, relue par des assistants, testée par vous, mise en ligne avec des contrôles automatiques, des clés protégées, puis trouvée sur Google. Comptez six séances de deux à trois heures.

Avant de commencer

Le fil rouge : le salon de coiffure « Salon Lila » veut un carnet de réservations. Le tutoriel rapide en a fait un prototype. Ici, on reprend chaque étape de la méthode pour une appli fiable, avec le pack Next.js de Pulse (pulse-next).

User storyCe que l'appli permet
US-001Une cliente prend rendez-vous : elle choisit une prestation, un créneau libre, puis donne son nom et son e-mail.
US-002La coiffeuse voit les rendez-vous du jour. Cette page est réservée au salon : il faut se connecter.
US-003La cliente reçoit un rappel par e-mail la veille de son rendez-vous.
US-004(Facultative) La cliente verse un acompte en ligne.

Ce qu'il vous faut :

  • tout ce que liste la page Prérequis : Git, Node.js, Claude Code, le plugin Pulse, et VS Code avec l'extension Claude Code ;
  • le pack Next.js, à installer une fois (voir plus bas) ;
  • un compte GitHub (la copie en ligne du projet), et en cours de route un compte Neon (la base de données) et un compte Vercel (l'hébergeur). Pulse vous guide pour chacun, au moment où il sert.

Travailler dans VS Code

Ce tutoriel utilise VS Code avec l'extension Claude Code : vous discutez avec Claude dans un panneau, et vous voyez les fichiers du projet juste à côté. Les menus de VS Code peuvent être en anglais : le nom anglais est donné entre parenthèses.

  1. Ouvrir le dossier du projet : menu Fichier → Ouvrir le dossier… (File → Open Folder…), puis choisissez le dossier. Ses fichiers s'affichent à gauche, dans l'explorateur de fichiers.
  2. Ouvrir le panneau Claude Code : cliquez sur l'icône en forme d'étincelle en haut à droite de l'éditeur (elle apparaît quand un fichier est ouvert), ou sur la même icône dans la barre de gauche, qui liste vos conversations. Autre chemin : Ctrl + Maj + P (Cmd + Maj + P sur Mac), tapez « Claude Code », puis choisissez Open in New Tab.
  3. Taper les commandes : toutes les commandes /pulse:… de cette page se tapent dans la zone de saisie du panneau Claude Code.

Trois gestes de VS Code servent tout au long du tutoriel :

  • Lire un document produit par Pulse (PRD, user stories, carnet de route) : cliquez sur le fichier dans l'explorateur, puis Ctrl + Maj + V (Cmd + Maj + V sur Mac) pour l'afficher mis en forme.
  • Lancer une commande technique, seulement quand Pulse vous le demande (par exemple lancer l'appli) : menu Terminal → Nouveau terminal (Terminal → New Terminal). Un terminal s'ouvre en bas, déjà placé dans le dossier du projet.
  • Voir les versions enregistrées : l'icône du contrôle de source, dans la barre de gauche (Ctrl + Maj + G), montre les fichiers modifiés et l'historique des enregistrements.

Pour installer le pack Next.js, tapez dans le panneau Claude Code la commande ci-dessous : la fenêtre de gestion des plugins s'ouvre. Dans l'onglet Plugins, cherchez pulse-next et cliquez sur Install.

/plugins

Une séance correspond à une partie de cette page. Entre deux étapes longues, repartez d'une conversation neuve, puis lancez la commande suivante : la conversation repart légère, et Pulse retrouve tout grâce aux fichiers du projet et à sa mémoire. Pour cela, tapez /clear dans le panneau ; si l'extension ne le propose pas, ouvrez une nouvelle conversation avec Ctrl + Maj + Échap (Cmd + Maj + Échap sur Mac).

Conseil : vous préférez le terminal ou l'application Claude Desktop ? Tout le tutoriel marche aussi : tapez les mêmes commandes /pulse:… dans claude ou dans Claude Desktop, ouvert sur le dossier du projet. Dans le terminal, le pack s'installe avec claude plugin install pulse-next@pulseia, et /clear repart d'une conversation neuve.

Conseil : vous avez fait le prototype ? Le plus simple est de repartir d'un dossier neuf, pour vivre chaque étape. Si vous préférez continuer dans le dossier du prototype, chaque commande vous demande si elle doit compléter le document existant ou repartir de zéro.

La connexion marche en local mais pas en ligne

L'adresse du site déclarée pour la connexion est encore celle de votre ordinateur. En ligne, elle doit être l'adresse du site : Pulse la règle avec vous dans les variables de l'hébergeur, puis relance la mise en ligne.

Pour reprendre plus tard : tapez /pulse:status. La ligne « En ligne » montre l'adresse du site, et la prochaine étape conseillée prépare la mise en ligne pour de vrai.

4 Séance 4 : mettre en ligne pour de vrai 2 à 3 h

Objectif : un site qui se vérifie tout seul avant chaque publication, des clés bien rangées, une sécurité contrôlée. C'est ce qui sépare un prototype d'une appli prête pour de vrais clients.

Les contrôles automatiques : /pulse:cicd

Objectif : qu'une erreur soit signalée par une croix rouge sur GitHub avant d'arriver sur le site. Environ 30 min

/pulse:cicd

Pulse écrit pour GitHub un contrôle qui tourne à chaque envoi et sur chaque proposition de version parallèle : clés absentes du code, chaque scénario prévu avec son test, dépendances sans faille grave connue, règles du code, tests, construction. Il l'essaie d'abord sur votre ordinateur, l'envoie, puis vous montre le premier passage. Il propose ensuite de recevoir chaque semaine les nouvelles versions des dépendances, vérifiées par ce contrôle avant que vous les acceptiez. Voir /pulse:cicd.

Si vous publiez par versions parallèles, protégez aussi la version principale : une proposition la rejoindra seulement si ses contrôles sont au vert.

/pulse:cicd proteger

Attention : avec la protection, l'envoi direct sur la version principale peut être refusé. Passez alors les plans en cours en version parallèle : /pulse:refine US-003 "changer l'envoi". Selon l'offre de GitHub, la protection peut aussi être indisponible pour un dépôt privé gratuit : la croix rouge reste visible sur chaque proposition.

Le premier passage affiche une croix rouge

Pulse lit le journal de l'étape en échec, vous l'explique et corrige. Après deux essais sans succès, il s'arrête et propose /pulse:get-help.

Le mode production : /pulse:deploy production

Objectif : préparer le site « pour de vrai » : variables, services, surveillance, retour arrière. Environ 45 min

/pulse:deploy production

Pulse fait vérifier le projet par l'hébergeur avant chaque publication : si un contrôle échoue, l'ancienne version reste en ligne. Il dresse ensuite la liste des variables du site, sans aucune valeur, et envoie celles qui manquent à Vercel, chaque envoi avec votre accord. Il vous explique la différence entre une prévisualisation et la production, vous aide à choisir une seule adresse officielle (votre nom de domaine), à créer une sonde qui vous prévient par e-mail si le site ne répond plus, et vous montre comment revenir à la version précédente. Voir /pulse:deploy.

Risque : ces réglages changent le site de vos clientes. Lisez chaque demande d'accord de Claude Code avant d'accepter. Les valeurs des clés passent seulement par votre éditeur, le fichier .env et l'hébergeur, jamais par la conversation. En cas de souci, la section « Retour arrière » de docs/technical.md remet la version précédente en ligne.

Résultat attendu : les contrôles tournent avant chaque publication, toutes les variables sont présentes en production, une sonde surveille le site, et docs/technical.md décrit le retour arrière.

L'audit de sécurité : /pulse:security

Objectif : vérifier que seul ce que le serveur bloque est vraiment interdit. Environ 45 min

/pulse:security

Un assistant passe tout le projet au crible de la liste de sécurité Pulse, sans rien modifier. Pulse vous donne un niveau global, explique chaque point bloquant par ce qu'un inconnu pourrait faire, puis déroule avec vous « le test du cambrioleur » : des essais à faire vous-même, un à la fois. Il propose enfin de corriger, en commençant par les points bloquants. Voir /pulse:security.

Niveau : 🟠 · 0 point bloquant · 2 points à surveiller. Test 2 sur 5 : déconnectez-vous, puis ouvrez directement l'adresse du carnet du jour. Que voyez-vous ?

Protégé ✅ : je suis renvoyée vers la connexion.

Test 3 sur 5 : envoyez le formulaire de réservation dix fois de suite, très vite.

Attention : faites ces essais sur votre propre site, avec de faux comptes et de fausses réservations, puis supprimez-les.

Résultat attendu : docs/securite.md contient l'audit et vos résultats du test du cambrioleur, sans aucun point bloquant restant.

Les clés du projet : /pulse:secrets

Objectif : savoir où sont vos clés, savoir les changer, et savoir quoi faire si l'une d'elles est vue. Environ 20 min

/pulse:secrets

L'inventaire liste chaque clé par son nom, avec sa présence dans .env et chez l'hébergeur, sans jamais afficher de valeur. Pulse signale les points à corriger, du plus grave au moins grave, et tient docs/secrets.md à jour. Deux autres actions servent plus tard :

  • /pulse:secrets renouveler BETTER_AUTH_SECRET : la nouvelle clé d'abord, l'ancienne coupée seulement après votre « Ça marche » en production. Aucune coupure.
  • /pulse:secrets fuite : dès qu'une clé a été vue ailleurs que dans .env (dépôt, conversation, capture d'écran, alerte de GitHub). L'ancienne clé est rendue inutilisable tout de suite, puis remplacée.

Le détail est sur la page /pulse:secrets.

/pulse:secrets fuite

On s'en occupe tout de suite. Première chose : rendre l'ancienne clé inutilisable chez le fournisseur. Je vous guide. Quelle clé ? (liste tirée de l'inventaire, ou « Je ne sais pas laquelle »)

Risque : une clé permet d'agir à votre place. Ne la collez jamais dans la conversation, dans un e-mail ou sur une capture. Si c'est arrivé, lancez /pulse:secrets fuite aussitôt : révoquer d'abord, remplacer ensuite.

Pour reprendre plus tard : tapez /pulse:status. La ligne « Contrôles » montre le dernier passage des contrôles automatiques ; s'il est en échec, c'est la première chose que Pulse vous propose de régler.

5 Séance 5 : US-003, le rappel la veille Environ 2 h

Objectif : ajouter une fonction à un site déjà en ligne, avec toute la routine : version parallèle, contrôles au vert, prévisualisation, puis acceptation par vous.

Construire le rappel par e-mail

Objectif : chaque cliente reçoit un e-mail la veille de son rendez-vous. Environ 1 h 30

/pulse:spirc US-003

Cette fois, demandez une version parallèle dès l'annonce des réglages. La spec pose les vraies questions du métier : à quelle heure partent les rappels, que contient l'e-mail, que se passe-t-il pour un rendez-vous pris le jour même ? Le plan reprend la recette « email » du pack pour l'envoi. Le déclenchement chaque jour n'a pas de recette toute prête : Pulse le conçoit dans le plan et vous le présente avant de construire.

Pour vos tests, Pulse vous guide pour installer Mailpit sur votre ordinateur : il capture tous les e-mails envoyés en local, et rien ne part vers de vraies adresses. Vous lisez les rappels dans votre navigateur, sur http://localhost:8025.

Envoyer de vrais e-mails en ligne

Objectif : brancher un vrai service d'envoi pour le site en ligne. Environ 20 min

Pour essayer, un compte Gmail créé pour le projet (jamais votre compte personnel) suffit, avec un mot de passe d'application. Pour un vrai lancement, Pulse conseille le service d'envoi d'un fournisseur, avec le nom de domaine du salon. La valeur réelle part en production ; les prévisualisations reçoivent une valeur de test.

Risque : chaque prévisualisation travaille sur une copie des vraies données, adresses des clientes comprises. Avec le vrai service d'envoi, une version d'essai pourrait écrire à de vraies clientes. Gardez le service réel pour la production seulement, comme Pulse le propose. Le mot de passe d'envoi, vous le collez vous-même dans .env (ouvert dans VS Code, onglet fermé ensuite) puis chez l'hébergeur ; il ne passe jamais par la conversation.

Accepter la proposition

Objectif : publier US-003 quand tout est au vert. Environ 10 min

Sur GitHub, la proposition d'US-003 montre ses contrôles automatiques et l'adresse de prévisualisation. Contrôles au vert, prévisualisation testée : cliquez « Merge ». Le site se met à jour tout seul. Revenez ensuite dans Claude Code : Pulse récupère la version principale à jour et retire la version parallèle devenue inutile.

Résultat attendu : US-003 est en ligne. Une réservation pour demain, faite avec votre propre adresse, vous vaut un rappel la veille.

Et l'acompte, US-004 ?

US-004 est Optionnelle : elle attend son tour. Le jour où vous la lancez avec /pulse:spirc US-004, la recette « paiement » du pack l'installe en mode test : aucune vraie carte, aucun vrai argent. Passer au paiement réel reste votre décision, au moment de la mise en ligne : compte du service de paiement activé, conditions de vente, mentions légales.

Pour reprendre plus tard : tapez /pulse:status. Une proposition encore ouverte sur GitHub y est rappelée, tout comme une version parallèle qu'il reste à retirer.

6 Séance 6 : être trouvé Environ 2 h, puis tous les 28 jours

Objectif : que les gens qui cherchent un coiffeur dans le quartier trouvent le salon, et que la page s'ouvre vite sur leur téléphone.

Les textes des pages : /pulse:rediger

Objectif : une page d'accueil qui parle aux clientes, avec des faits vrais. Environ 30 min

/pulse:rediger accueil

La première fois, Pulse fixe la voix du site avec vous : vous ou tu, trois traits de ton, la promesse du salon en une phrase. Puis il vous interroge sur la page : pour qui, quel bouton, quels faits (adresse, horaires, prestations). Un fait inconnu reste marqué « [à compléter] ». Un contrôle vérifie que le texte ne sonne pas écrit par une IA. Vous choisissez ensuite de le garder de côté ou de l'intégrer à la page. Voir /pulse:rediger.

Le référencement : /pulse:seo

Objectif : vérifier que Google peut entrer, lire et garder vos pages. Environ 30 min

/pulse:seo

Les fondations ont été posées dans le plan d'US-002. L'audit lit maintenant le site servi, comme un robot, et range ses constats en quatre questions : Google peut-il venir, garder la page, comment se présente-t-elle, mérite-t-elle d'être choisie ? Puis deux actions utiles : /pulse:seo textes, où vous choisissez entre deux titres et deux descriptions par page, et /pulse:seo ia, où vous décidez ce que les assistants IA peuvent faire du site. Voir /pulse:seo.

La vitesse : /pulse:perf

Objectif : voir ce que vit une cliente sur téléphone, puis l'améliorer, chiffres à l'appui. Environ 30 min

/pulse:perf

Pulse mesure 3 à 5 pages comme sur un téléphone moyen en 4G, trois fois chacune, et garde la valeur du milieu. Sans clé Google, il mesure sur votre ordinateur : c'est très bien pour commencer. Il donne une phrase de verdict par page et trois priorités au plus. Ensuite, /pulse:perf corriger applique les priorités choisies et annonce seulement ce qui va vraiment mieux ; /pulse:perf suivre propose la mesure chez les vrais visiteurs et une vérification chaque semaine. Voir /pulse:perf.

Prévenir Google : /pulse:seo lancer et /pulse:search-console relier

Objectif : prouver à Google (et à Bing) que le site est à vous, et déclarer son plan. Une seule fois. Environ 30 min

/pulse:seo lancer
/pulse:search-console relier

Ces deux commandes demandent le site sur son adresse définitive. Vous agissez sur Search Console avec votre compte Google, guidée une étape à la fois : ajouter la propriété, la faire vérifier, déclarer le plan du site, l'importer dans Bing. Pour que Pulse lise vos chiffres, le plus simple est d'exporter un fichier depuis Search Console quand vous voulez un rapport : aucun secret, rien à installer. Voir /pulse:search-console.

/pulse:search-console relier

Search Console, c'est le tableau de bord que Google vous tend : ce qu'il a trouvé sur votre site, et ce que les gens ont tapé pour vous trouver. Votre site est sur votre propre nom de domaine : on le vérifie par un enregistrement chez le gestionnaire du domaine. Ouvrez search.google.com/search-console et choisissez « Ajouter une propriété ».

Premières données dans 2 à 3 jours. Premier vrai rapport dans 28 jours, avec /pulse:search-console lire.

Attention : reliez Search Console une fois le nom de domaine définitif en place. Un changement d'adresse ensuite obligerait à recommencer.

Risque : si vous choisissez la connexion Google en lecture seule, Pulse vous demande seulement le chemin du fichier d'identifiants téléchargé, jamais son contenu. Gardez ce fichier hors du projet.

Résultat attendu : la propriété est vérifiée, le plan du site est déclaré, et docs/technical.md note la date du prochain rapport.

Pour reprendre plus tard : tapez /pulse:status. La ligne « Référencement » rappelle la date du prochain rapport conseillé ; le moment venu, Pulse vous propose /pulse:search-console suivre.

7 La liste « prête pour de vrais clients »

Avant d'annoncer le site à vos clientes, cochez chaque ligne. Chacune renvoie à l'étape qui la règle.

  • US-001 et US-002 sont terminées, et vous les avez testées vous-même, en local puis en ligne (séance 2, séance 3).
  • Les contrôles automatiques passent au vert à chaque envoi (/pulse:cicd).
  • Le site vit sur son adresse définitive, avec une offre d'hébergement qui autorise un usage commercial.
  • Le mode production est en place : variables en ligne, sonde de disponibilité, retour arrière écrit (/pulse:deploy production).
  • L'audit de sécurité ne montre aucun point bloquant, et vous avez fait le test du cambrioleur (/pulse:security).
  • L'inventaire des clés est à jour dans docs/secrets.md (/pulse:secrets).
  • Les e-mails partent par un vrai service d'envoi, au nom de domaine du salon, et seulement depuis la production (séance 5).
  • Une page dit quelles données vous gardez (nom, e-mail), pourquoi et combien de temps. Vous pouvez la faire écrire avec /pulse:rediger ; relisez chaque fait.
  • Search Console est relié, et la vitesse de l'accueil est mesurée (séance 6).

9 Si quelque chose ne va pas

Rien n'est perdu : chaque version est enregistrée, et chaque situation a sa commande.

Un bouton ne marche plus, ou un message d'erreur s'affiche

Lancez /pulse:fix "le bouton Réserver ne fait rien" en décrivant ce que vous voyez. Pulse cherche la vraie cause avant de corriger, puis vous explique comment l'éviter.

Je veux revenir en arrière

/pulse:annuler abandonne les changements en cours, annule une tâche enregistrée ou revient à une version précédente. Il vous montre un aperçu et attend votre accord ; tout se récupère.

La nouvelle version en ligne est cassée

Suivez la section « Retour arrière » de docs/technical.md : chez Vercel, la version précédente revient en ligne en quelques clics. Corrigez ensuite avec /pulse:fix, puis rétablissez la mise en ligne automatique comme indiqué dans cette même section.

Les contrôles automatiques sont rouges

/pulse:status le signale en premier. Lancez /pulse:fix avec le message de l'étape en échec ; pour des erreurs rouges dans le code, /pulse:auto-fix.

Une clé a été vue

/pulse:secrets fuite, tout de suite : la clé est d'abord rendue inutilisable chez le fournisseur, puis remplacée.

Je suis bloquée et Pulse n'y arrive pas

/pulse:get-help prépare une demande d'aide claire, sans vos secrets, à transmettre à une personne qui programme, avec les bons endroits où la poser.

Retrouvez toutes les commandes dans la liste des commandes, et l'autre parcours dans les tutoriels.
