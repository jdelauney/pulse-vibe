Tutoriel 3 · Après le prototype, quatre séances

Du prototype à la production

Le prototype du salon a convaincu : la coiffeuse veut l'utiliser pour de bon. Inutile de tout recommencer. Ce tutoriel reprend le projet du tutoriel rapide là où il s'est arrêté, passe en mode complet, et le mène jusqu'à une appli prête pour de vrais clients.

Le mode rapide a sauté volontairement des étapes : les entretiens approfondis, le test après chaque tâche, une partie des tests automatiques, la sécurité approfondie, Google. On les reprend ici, dans le même dossier, sans perdre ce qui marche déjà. Pour vivre chaque étape depuis le début, dans un dossier neuf, suivez plutôt le tutoriel complet.

1 Passer en rythme complet 5 minutes

Objectif : que chaque prochaine user story soit construite avec tout le soin du mode complet.

Le parcours express a réglé le projet sur le rythme rapide : chaque réalisation le prend d'office, sans vous demander. Ce réglage est noté dans CLAUDE.md, dans votre profil. Demandez simplement à Pulse de le changer. (Pour qu'il vous demande le rythme à chaque réalisation, dites plutôt « demande-moi le rythme à chaque fois ».)

Passe le projet en rythme complet.

C'est fait : dans votre profil, « Rythme : complet ». Désormais, chaque tâche est relue et essayée par deux assistants, puis testée par vous, avant d'être enregistrée.

Rythme rapide (le prototype)Rythme complet (à partir d'ici)
Tests automatiquesLes essentiels : enregistrements et règles d'accèsÉcrits avant le code, pour chaque scénario de la spec (avec « Tests d'abord »)
RelectureUne seule, pour toute la user storyÀ chaque tâche, par deux assistants
Votre testUn seul parcours, à la finAprès chaque tâche
Construction de l'appliÀ la mise en ligne seulementVérifiée à chaque tâche

Le site est maintenant en ligne : chaque tâche envoyée sur la version principale y partirait aussitôt. Au démarrage de la prochaine réalisation, choisissez donc la version parallèle : vous essaierez le travail sur une adresse de prévisualisation, puis vous l'accepterez vous-même. Le détail est dans le tutoriel complet.

Résultat attendu : CLAUDE.md indique « Rythme : complet » dans votre profil.

2 Recueillir les retours, compléter la description Environ 1 h 30

Objectif : que les documents du projet disent ce que le salon veut vraiment, après avoir essayé le prototype.

Noter les retours

Créez un dossier docs/depart/ et déposez-y les retours de la coiffeuse : un fichier de notes, un e-mail recopié, des captures d'écran annotées. Pulse les lira avant de vous poser ses questions.

docs/depart/retours-coiffeuse.md

Exemple de contenu : « Les clientes demandent un rappel la veille. Une coupe homme dure 20 minutes, pas 30. J'aimerais pouvoir bloquer mes jours de congé. »

Approfondir l'idée : /pulse:brainstorm

/pulse:brainstorm docs/depart/

Votre brief existe déjà : choisissez Compléter. Pulse lit vos notes, vous montre ce qu'il en a compris (« ✔ D'après vos documents… »), puis pose seulement les questions qui restent. C'est l'entretien que le parcours express avait résumé en une conversation. Voir /pulse:brainstorm.

✔ D'après vos documents (retours-coiffeuse.md) : les clientes veulent un rappel la veille, et vous voulez bloquer vos jours de congé. C'est bien ça ?

Oui. Et les congés, je les connais un mois à l'avance.

Retrier la première version : /pulse:prd

/pulse:prd

Choisissez Compléter. Pulse range les nouvelles idées : le rappel la veille, les jours de congé, l'acompte. Pour chacune, vous dites si elle est indispensable à la première version ou si elle peut attendre. Voir /pulse:prd.

Ajouter les user stories : /pulse:us

/pulse:us

Choisissez Compléter : US-001 et US-002 gardent leur numéro, les nouvelles prennent la suite (US-003 le rappel la veille, US-004 l'acompte…). Chaque nouvelle user story est vérifiée et prête à préparer. Voir /pulse:us.

Conseil : vous voulez voir le carnet du salon avant qu'il soit codé ? /pulse:ui maquettes US-002 dessine plusieurs versions de l'écran, à comparer dans votre navigateur. Faites-le après la spec d'US-002, avant son plan.

Résultat attendu : le brief, le PRD et le référentiel des user stories tiennent compte des retours ; les nouvelles user stories ont leur fichier dans leur groupe.

3 Consolider la prise de rendez-vous Environ 1 h

Objectif : donner à US-001, faite en rythme rapide, le niveau de soin du mode complet, sans la refaire.

Les tests qui manquent : /pulse:test ecrire US-001

/pulse:test ecrire US-001

En rythme rapide, seuls les tests essentiels ont été écrits. Un assistant écrit maintenant ceux qui manquent, à partir des scénarios de la spec et des critères d'acceptation, sans toucher au code de l'appli. Un autre les lance et trie chaque échec : un test qui échoue ici révèle souvent un vrai défaut du prototype. Voir /pulse:test.

US-001 : 3 scénarios de la spec n'ont pas encore de test. Je les fais écrire. ✅ 2 réussis · ❌ 1 échoue : « un créneau déjà pris ne se réserve pas deux fois », quand deux clientes valident à la même seconde. C'est un défaut du code, pas du test. Je vous propose de le corriger avec /pulse:fix.

Un défaut trouvé se corrige avec /pulse:fix, puis s'enregistre avec /pulse:commit.

Un premier contrôle de sécurité : /pulse:security rapide

/pulse:security rapide

En deux minutes, Pulse vérifie les points les plus graves : clés hors du code, formulaire contrôlé côté serveur, pages réservées vraiment protégées. L'audit complet viendra à l'étape 5, une fois le carnet du salon construit. Voir /pulse:security.

Attention : le prototype a peut-être déjà reçu de vraies réservations, si vous avez partagé son adresse. Traitez-les comme de vraies données : ne les copiez nulle part, et prévenez les personnes concernées si l'appli change de règle.

Résultat attendu : chaque scénario automatisé de la spec d'US-001 a son test, tous réussis ; le contrôle rapide ne montre aucun point bloquant.

4 Construire le carnet du salon en mode complet 2 à 3 h

Objectif : la coiffeuse se connecte et voit les rendez-vous du jour, et personne d'autre ne les voit. C'est la dernière user story de la première version.

/pulse:spirc US-002

Votre profil dit « complet » : Pulse ne vous demande plus le rythme. Au démarrage, il pose seulement les tests (choisissez « Tests d'abord ») et la façon d'envoyer le travail (choisissez la version parallèle). Puis il écrit la spec et le plan avec vous, et réalise chaque tâche : les tests d'abord, le code, deux assistants qui relisent et essaient, votre test, l'enregistrement. Le déroulé est animé sur la page /pulse:spirc.

/pulse:spirc US-002

Quels tests ? → Tests d'abord (Recommandé) Comment envoyer le travail de US-002 ? → Une version parallèle pour l'US, publiée quand vous l'acceptez sur le site du dépôt

T6 – Se connecter au carnet du salon. Les tests sont écrits : ils échouent, c'est attendu tant que le code n'existe pas. Relecture : ✅ Validé · Vérification : ✅ Prouvé. 🧪 À vous de tester : votre fiche (4 étapes, environ 3 minutes). Étape 1 : ouvrez une fenêtre de navigation privée, puis l'adresse du carnet du jour ; vous devez arriver sur la page de connexion. Le test est-il concluant ?

Oui, tout fonctionne

Comme US-002 est la dernière user story Indispensable, son plan se termine par les fondations du référencement, puis par « Mettre en ligne la première version ». Avec la version parallèle, c'est vous qui acceptez la proposition sur GitHub, après avoir essayé l'adresse de prévisualisation. Le détail de la connexion et de la mise en ligne est dans le tutoriel complet, séance 3.

Risque : accepter la proposition met la nouvelle version en ligne, sur le site que les clientes utilisent déjà. Essayez d'abord l'adresse de prévisualisation. Pulse ne l'accepte jamais à votre place.

Conseil : pour enchaîner plusieurs user stories, par exemple US-002 et le rappel la veille, /pulse:spirc US-002 US-003 prépare d'abord avec vous leurs specs et leurs plans, puis les réalise à la suite. Vous testez alors à la fin, une user story après l'autre. Avec /pulse:status ligne, l'avancement s'affiche en bas de l'écran.

Résultat attendu : le carnet du jour est en ligne, réservé au salon ; chaque tâche d'US-002 a son rapport de relecture et votre test concluant.

Pour reprendre plus tard : relancez /pulse:spirc US-002 ; Pulse reprend à la tâche en cours, test compris.

5 Mettre en ligne pour de vrai 2 à 3 h

Objectif : passer d'une adresse de démonstration à un site qui se vérifie tout seul, sur son vrai nom de domaine, avec des clés bien rangées.

Quatre commandes, dans l'ordre. Chacune est décrite en détail dans le tutoriel complet, séance 4 : vous faites exactement la même chose, sur votre projet existant.

CommandeCe qu'elle apporte au prototype
/pulse:cicd, puis /pulse:cicd protegerUn contrôle qualité sur GitHub à chaque envoi et sur chaque proposition : une croix rouge vous prévient avant que l'erreur n'arrive sur le site. La protection empêche une proposition en échec de rejoindre la version principale.
/pulse:deploy productionLes variables de production, votre nom de domaine à la place de l'adresse en .vercel.app, une sonde qui vous prévient si le site ne répond plus, et le retour arrière écrit.
/pulse:securityL'audit complet, cette fois, et le test du cambrioleur, fait par vous.
/pulse:secretsL'inventaire de vos clés, sans aucune valeur affichée, et la façon de les changer sans couper le site.

Attention : l'offre gratuite de Vercel, suffisante pour le prototype, est réservée à un usage non commercial. Pour un vrai salon, passez à l'offre payante avant d'annoncer le site.

Conseil : une habitude du salon se vérifie dans le code ? Faites-la retenir avec un contrôle : /pulse:memory retenir "les durées des prestations viennent toutes du fichier des prestations". Pulse peut lui ajouter un contrôle, que chaque enregistrement vérifiera.

Résultat attendu : les contrôles automatiques passent au vert, le site répond sur son nom de domaine, l'audit de sécurité ne montre aucun point bloquant, et docs/secrets.md est à jour.

6 Le rappel la veille, puis être trouvé Environ 4 h, en deux séances

Objectif : ajouter une fonction à un site en ligne, avec toute la routine, puis faire connaître le salon.

  • Le rappel la veille : /pulse:spirc US-003, en version parallèle. Les e-mails d'essai restent sur votre ordinateur ; seul le site en production écrit aux vraies clientes. Le détail : tutoriel complet, séance 5.
  • Être trouvé : /pulse:rediger accueil pour les textes, /pulse:seo pour le référencement, /pulse:perf pour la vitesse, puis /pulse:seo lancer et /pulse:search-console relier, une fois le nom de domaine définitif en place. Le détail : tutoriel complet, séance 6.

Attention : le prototype a été mis en ligne sans se soucier de Google. Le référencement repart donc de la nouvelle adresse : reliez Search Console seulement quand le nom de domaine du salon est en place.

7 Prête pour de vrais clients

Objectif : vérifier qu'il ne reste rien du prototype qui gênerait de vrais clients.

  • Le profil du projet est en rythme complet (étape 1).
  • Les retours de la coiffeuse sont dans le brief, le PRD et les user stories (étape 2).
  • US-001 a tous ses tests, et le défaut éventuel trouvé est corrigé (étape 3).
  • US-002 est en ligne, construite et testée tâche par tâche (étape 4).
  • Le site vit sur son nom de domaine, avec une offre d'hébergement qui autorise un usage commercial (étape 5).
  • Toute la liste « prête pour de vrais clients » du tutoriel complet est cochée : la voir.

Ensuite, l'appli vit : quelques gestes réguliers suffisent à la garder à jour, sûre et trouvable. Ils sont décrits dans l'entretien régulier. Et si quelque chose ne va pas, chaque situation a sa commande : si quelque chose ne va pas.

Pour reprendre plus tard : /pulse:status ; une nouvelle idée devient une nouvelle user story, avec /pulse:spirc US-003 "ajouter…" ou /pulse:spec "…".
