Étape 4 · Construire

/pulse:implement

Réaliser une tâche d'un plan et l'expliquer, en coulisse ou devant vous, au besoin dans un dossier à part ; sans tâche, boucler sur tout le plan (réaliser, relire et vérifier, corriger, enregistrer, tâche suivante).

    Description

    Avec un numéro de tâche, /pulse:implement réalise cette tâche du plan, puis vous l'explique : ce qui a changé, fichier par fichier, une notion de programmation tirée du code (« 💡 la notion du jour »), et les étapes pour la tester vous-même. La relecture et l'enregistrement viennent ensuite, avec /pulse:review puis /pulse:commit.

    Sans numéro de tâche, elle réalise tout le plan, en boucle. Chaque tâche est réalisée, relue et vérifiée par deux assistants qui ne l'ont pas écrite, testée par vous, corrigée si besoin, puis enregistrée avant de passer à la suivante. Chaque tâche a sa propre version enregistrée.

    Au démarrage, une seule série de questions : Pulse code-t-il en coulisse (un assistant spécialisé code à part, la conversation reste légère) ou devant vous (vous voyez chaque étape) ? Faut-il écrire les tests d'abord, travailler dans un dossier à part, et comment envoyer le travail ? Avec le profil « Jamais programmé », Pulse prend les réglages conseillés et vous les annonce en une phrase.

    Pourquoi l'utiliser

    • Une tâche à la fois. Chaque tâche est petite, testée et enregistrée seule : un problème se repère tout de suite.
    • Vous apprenez en chemin. À chaque tâche, une notion de programmation tirée de votre propre code, expliquée simplement et ajoutée à votre lexique.
    • Le code suit vos choix. Pulse code seulement ce que demande la tâche, avec les outils retenus, l'apparence choisie et vos maquettes. Une idée en plus est notée « En attente » dans le PRD, pour plus tard.
    • Tout le plan, sans rien oublier. Sans numéro de tâche, la boucle enchaîne réaliser, relire, tester, corriger et enregistrer, pour chaque tâche.

    Comment la lancer

    /pulse:implement <US-XXX> [T3]

    Entre crochets [ ] : facultatif. Entre chevrons < > : à remplacer par votre valeur. La barre | sépare les choix possibles. Sans tâche : tout le plan.

    • L'US : celle dont vous réalisez le plan, par exemple US-001. Absente ou introuvable, Pulse liste les plans (en premier celui qui a une tâche en cours) et vous demande lequel.
    • La tâche (facultative) : par exemple T3, pour réaliser cette seule tâche. Sans elle, Pulse réalise toutes les tâches restantes du plan, dans l'ordre.
    • Les raccourcis (pour les habitués, facultatifs) : ils répondent d'avance aux questions du démarrage. Placez-les avant l'US ; ils se regroupent (-sw vaut -s -w).
      • -s : en coulisse. Un assistant spécialisé code à part ; conseillé pour tout un plan.
      • -d : devant vous. Pratique pour apprendre en voyant chaque étape.
      • -w : dans un dossier à part, sur sa propre branche. Utile quand une autre session travaille sur le même dossier.
      • -t : tests d'abord. Un assistant écrit les tests de la tâche, on les voit échouer, puis le code doit les faire passer.
      -s et -d ensemble se contredisent : Pulse vous demande lequel garder.
    /pulse:implement US-001 T3
    /pulse:implement US-001
    /pulse:implement -d US-001 T3

    Sur tout le plan, s'y ajoute une version enregistrée dans Git par tâche. Avec un numéro de tâche, la tâche reste « en cours » : elle sera terminée après la relecture et l'enregistrement.

    Risques et précautions

    • Vos clés secrètes restent chez vous. Vous les écrivez vous-même dans le fichier local prévu ; Pulse ajoute seulement leur nom dans .env.example.
    • Une bibliothèque s'ajoute seulement avec votre accord, avec une version fixée.
    • Les décisions vous reviennent. Dès qu'un choix apparaît, Pulse s'arrête et vous présente les options et leurs conséquences.
    • Claude Code vous demande votre accord pour lancer l'application et l'essayer pendant la relecture, et pour envoyer le travail sur le dépôt en ligne.

    Attention : une tâche « Mettre en ligne… » ne se fait pas ici. Pulse s'arrête avant elle et vous propose /pulse:deploy.

    Risque : sur la branche principale, chaque envoi peut mettre votre site en ligne à jour, si le déploiement automatique est en place. Pour tester avant de publier, choisissez au démarrage « Une version parallèle pour l'US, publiée quand vous l'acceptez sur le site du dépôt ».

    Problèmes et solutions

    Pulse me propose d'abord /pulse:review et /pulse:commit

    Des changements non enregistrés concernent une autre tâche. Une version enregistrée = une seule tâche : relisez et enregistrez d'abord celle-là, puis relancez la commande.

    La boucle s'arrête sur une tâche

    Il y a un blocage : une question sur votre besoin, une action à faire vous-même (créer un compte, saisir une variable chez l'hébergeur), ou un contrôle qui reste en échec. Répondez ou suivez les étapes données, puis Pulse reprend. Si un problème grave persiste après deux corrections, il vous propose /pulse:get-help.

    Il reste beaucoup d'erreurs rouges après la tâche

    Lancez /pulse:auto-fix : plusieurs assistants corrigent les erreurs des contrôles automatiques en même temps.

    Pulse me demande de choisir les outils avant de coder

    Il faut d'abord savoir avec quoi construire. Lancez /pulse:tech ; Pulse attend ce choix pour installer ou coder.

    J'ai fermé la conversation au milieu du plan

    Rien n'est perdu. Relancez /pulse:implement US-001 : une tâche en cours reprend à la bonne étape (relecture, correction, votre test ou enregistrement).

    Commandes liées

    • /pulse:plan : découpe la spec en tâches, avant cette commande.
    • /pulse:review : la relecture et votre test, après une tâche réalisée seule.
    • /pulse:commit : enregistre la tâche relue et testée.
    • /pulse:spirc : la même boucle, avec en plus la spec et le plan s'ils manquent.
    • /pulse:auto-fix : corrige les erreurs rouges restantes.
    • /pulse:deploy : met en ligne une fois le plan terminé.
